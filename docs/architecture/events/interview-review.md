# Kafka Interview Review (answers reference this design)

Why Kafka: durable fan-out (one order event → pay/notify/search/analytics) with replay; RabbitMQ suffices for queues but not log-replay at our scale path; direct HTTP couples availability (consumer-down = lost). Event = versioned business fact with envelope; domain (internal) vs integration (stable, what crosses Kafka). Outbox: dual-write Mongo+Kafka is unsafe (crash/phantom) → tx+publisher. Idempotency: ack-loss/redelivery inherently duplicate → inbox+version-guards. Exactly-once: no (at-least-once + idempotent = effective-once). Partitioning: key=aggregateId → per-entity order + parallelism; orderId key keeps order lifecycle ordered. Crash: offset uncommitted → redeliver → dedupe. Ack-lost: dup publish → same eventId → inbox skip. Retries: durable retry topics 1/5/30m ×5; poison → DLQ quarantine + alert. Replay: new group from offset/time; mail-safe via eventId dedupe + state re-check (no dup mails/payments). Schemas: additive + vN dual-publish. Kafka-down: outbox buffers, sync API alive, lag alert, catch-up on return. Lag: per-group metric, scale ≤ partitions. 1000x: 24–48 partitions hot topics, split inventory, keep 7d retention. Microservice cut: search/notify/audit already event-isolated — point existing topics at new services, dual-run, cutover.
