# Outbox + Inbox/Idempotency (ties Phase 4 schemas; why direct-publish is unsafe)

Direct Mongo→Kafka is unsafe: commit-then-publish loses events on crash between; publish-then-commit emits phantom events on abort; either breaks money/audit truth. Hence tx(biz + outbox PENDING) → publisher → Kafka; consumers idempotent anyway (ack-loss duplicates).
Outbox row: `{eventId, type, ver, aggregate{type,id}, topic, partitionKey, payload, corrId/causationId, status PENDING→CLAIMED→SENT|FAILED, attempts, nextRetryAt, createdAt, publishedAt, lastError}`; idx (status,nextRetryAt). Publisher (external worker, N instances safe): poll batch 100 `PENDING+due` → CLAIM via `findOneAndUpdate(status=PENDING→CLAIMED, leaseUntil=now+30s)` → publish → SENT (delete >7d); lease-expiry allows reclaim; FAILED after 10 attempts → alert (not DLQ — publisher never drops; DLQ is consumer-side). Metrics: backlog, publish-latency, fail-rate.
Inbox flow: validate envelope → `insert inbox{consumer,eventId}` (dup-key → skip as replay) → process + business-write in ONE tx → mark PROCESSED → commit offsets. Crash/restart/partial → redelivery replays safely. Payment/webhook/order/inventory/notify/search/analytics idempotency each: version-guarded transitions, amount-caps, versioned upserts, mail-dedupe by eventId — so 2nd/3rd delivery is a no-op read.
