# Reliability: Retries + DLQ + Poison + Replay + Failures + Backpressure

Transient (retry: net blip, Mongo timeout, SMTP 5xx): shared retry topics `retry.1m→5m→30m` (headers carry original topic/partition/offset, attempt#, error) max 5 attempts total; no in-memory setTimeout (durable topics only). Permanent (no retry: bad schema, unknown version, impossible state): straight to `{topic}.DLQ` with full envelope + `{reason, stack-lite, corrId, attemptHistory}`.
DLQ: 30d retention, dashboard + critical alert on growth, ops replay tool re-injects (fixed payload → original topic, new causationId) after code/config fix; poison (always-fails) stays quarantined — never infinite loop.
Replay: by offset/time-range into NEW consumer group (never reset prod offsets); search/analytics rebuild safe (versioned upserts, idempotent); mail-safe because notify dedupes by eventId and re-checks prefs + order state before sending (replayed `order.created` for already-PAID orders → skip mail, log). Side-effect protection matrix per consumer in catalog.
Failures: broker-down → publisher buffers in outbox (lag grows, alert; API still serves sync paths); ack-lost → dup → inbox skips; consumer-crash → rebalance + redeliver; partition-loss → replicas + replay; lag → scale instances (≤partitions) + batch-size up + downstream throttle (SMTP rate-cap, index bulk); retry-storm guard: jitter + per-consumer concurrency cap + DLQ overflow alert. Thresholds: lag>1k warn, >10k critical; DLQ>0 critical; outbox backlog>500 warn.
